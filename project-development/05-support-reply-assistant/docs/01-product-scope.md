# Product scope and investigation gates

Buyer hypothesis: support teams repeatedly looking up product information and reconstructing cases before replying. Interview agents, team leads, knowledge owners, integration owners and the buyer. Choose one specialty and channel first. Record existing alternatives, case volume, handling time, repeat contacts, error patterns and integration constraints.

Initial journey: import a permitted case -> review chronological summary and unresolved questions -> retrieve approved help sources -> generate a draft -> inspect internal evidence and missing facts -> edit/approve a precise revision -> copy/export the customer-facing reply for manual handoff. Screens include case queue, timeline/summary, draft/evidence workbench, source library, approval history, handoff history and team settings.

Upload/import-first scope: readable help articles and a documented JSON/CSV ticket format with stable case/message IDs. Qualify supported formats and languages in S02. Preserve message author, time zone, chronology, quoted text and public/private visibility. Attachment OCR, mailbox access, help-desk synchronization and direct sending are deferred pending separate qualification.

Distinguish the current customer's messages from agent statements, internal notes, approved policy and prior cases. A customer claim is not a verified order fact; a previous agent promise is not proof that an action happened. Selected historical tickets remain access-controlled and cannot become universal policy. Reusable examples need knowledge-owner approval and removal of unrelated customer identifiers.

Live order/account details require an authorized scoped query with identity, timestamp and freshness evidence. If no integration is configured, identify the missing fact for the agent; do not invent an order status, refund, delivery date or account change. No live integration is presumed available for the first pilot.

S01 go/narrow/stop requires buyer access, permitted articles/tickets, domain reviewer, baseline and measurable thresholds. S02 requires actual summary/draft results from a selected checkpoint, viable source parsing and an authenticated integration boundary. Failure can narrow to retrieval or summarization; that cannot count as an accepted reply-drafting release.

Commercial hypothesis from the opportunity document: per-agent subscription or usage-based business plan. Test willingness to pay against onboarding, actual review effort, runtime and support cost. Automatic sending, ticket closure, refunds, account changes and customer commitments without evidence are outside this initial product.
